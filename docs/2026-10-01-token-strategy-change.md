# 로그인 토큰 전략 변경

Access는 서버 조회 없이 검증하는 JWT로 유지한다. 기본 수명은 10분이며, 응답의 `expiresIn`은 실제 설정에서 계산한다. Refresh는 로그인마다 독립된 토큰 묶음(`family_id`)을 만들고, DB에 현재 토큰의 SHA-256 해시만 저장한다. HTTP 세션, access용 서버 세션, Redis는 추가하지 않는다.

## 발급·재발급·폐기

- 일반 API는 `token_use=access`와 유효한 역할만 받아들인다. 재발급은 `token_use=refresh`, 사용자 ID, 무작위 `jti`와 `family_id`를 요구한다.
- Refresh는 로그인 시점부터 최대 7일이다. 재발급할 때 새 `jti`를 발급하지만 만료 시각은 늘리지 않는다. 쿠키 수명도 남은 만료 시간에 맞춘다.
- DB 행 잠금으로 이전 토큰 해시 비교와 새 해시 저장을 직렬화한다. 이전 refresh 재사용이 감지되면 해당 묶음을 폐기한다. 401 응답으로 폐기가 롤백되지 않도록 회전 트랜잭션을 먼저 커밋한다.
- 로그인은 비밀번호 검사부터 refresh 저장까지 사용자 행을 잠근다. 비밀번호 변경과 겹친 이전 비밀번호 로그인이 새 refresh를 남기는 경쟁을 막는다.
- 로그아웃은 현재 로그인 묶음을, 비밀번호 변경·회원 탈퇴는 사용자의 모든 refresh 묶음을 폐기한다. 다른 기기의 로그인은 일반 로그아웃으로 종료하지 않는다.
- 이미 발급된 access는 로그아웃·비밀번호 변경 후에도 만료 전까지 유효하다. 즉시 access 폐기가 필요한 정책은 별도의 서버 상태 확인을 요구한다.
- 만료된 DB 행은 로그인 시 인덱스를 이용해 정리한다. 삭제량이 커지면 배치 정리로 옮긴다.

## 프런트 처리

초기 로그인 복원과 Axios는 같은 refresh Promise를 사용한다. 쿠키를 바꾸는 로그인·refresh·로그아웃·회원 탈퇴는 Web Locks로 같은 origin의 여러 탭에서 직렬화한다. 새 로그인이나 로그아웃 이후 도착한 이전 인증 결과는 적용하지 않으며, 이전 계정의 요청을 새 계정 토큰으로 재시도하지 않는다.

다른 탭의 알림이 늦어도 refresh 전후 access의 사용자 ID가 다르면 인증을 초기화하고 기존 요청을 중단한다. JWT payload 해석은 이 비교에만 쓰며, 서명과 권한 검증은 서버에서 수행한다. 폐기된 로그인 성공 응답도 쿠키 변경을 반영해 이전 인증을 초기화한다.

인증 종료가 확인된 401만 로그인 상태를 지운다. 네트워크·5xx 오류는 재시도 가능한 실패로 표시한다. 서버 로그아웃 실패를 성공으로 알리거나 페이지를 강제로 새로고침하지 않는다. 인증 쿠키 요청의 제한 시간은 10초다.

## 배포

1. 기존 MySQL DB에는 `code/backend/db/2026-10-01-refresh-tokens.sql`을 한 번 적용한다. 신규 DB 초기화용 `backup.sql`에도 같은 테이블이 포함되어 있다. 기존 데이터 볼륨에서는 `backup.sql`이 다시 실행되지 않는다.
2. Access 수명 환경변수는 `JWT_ACCESS_EXPIRATION_MS`이며 기본값은 `600000`이다. 이전 `JWT_EXPIRATION`은 더 이상 사용하지 않는다.
3. 서버·프런트를 함께 배포한다. 이전 JWT에는 용도·토큰 묶음 정보가 없으므로 기존 사용자는 한 번 다시 로그인해야 한다.
4. Refresh 쿠키는 `HttpOnly; Secure; SameSite=Lax; Path=/api/auth`다. 기존 `/api/auth/refresh` 경로 쿠키도 로그인·갱신·로그아웃·탈퇴 응답에서 삭제한다.
5. 프런트는 HTTPS 또는 localhost의 Web Locks 지원 브라우저에서 사용한다. 지원하지 않는 환경은 로그인·갱신을 안전하게 거부하고 안내를 표시한다.
6. 같은 API 쿠키를 사용하는 프런트는 하나의 origin으로 서비스한다. 서로 다른 origin은 브라우저 잠금을 공유하지 않으므로 동시 회전으로 재사용 차단이 발생할 수 있다.

회전 응답을 받은 뒤 클라이언트가 연결을 잃어 새 쿠키를 받지 못한 경우에도 이전 refresh는 재사용으로 차단된다. 사용자는 다시 로그인한다. 서버 토큰 상태와 쿠키를 다시 맞추려고 이전 refresh를 허용하지 않는다.

## 검증

실제 JWT, MockMvc, H2 DB 테스트로 토큰 바꿔 쓰기, 해시 저장, 고정 만료, 재사용 후 폐기 커밋, 로그인별 로그아웃, 비밀번호 변경·탈퇴, 동시 refresh, 단일 DB 연결 풀, 로그인·비밀번호 변경 경쟁을 검증한다. 프런트 테스트는 refresh 공유, 지연 응답, 로그인·로그아웃 경쟁, 일시 장애, 쿠키 요청 직렬화와 복원 재시도 화면을 검증한다.

- 백엔드 전체 테스트: 176개 통과, 기존 MySQL 주문 동시성 테스트 1개는 실행 조건에 따라 건너뛰었다.
- 프런트 전체 테스트: 75개 통과. TypeScript 검사와 프로덕션 빌드 통과.
- 프런트 lint: 작업 전부터 존재한 오류 8개가 남아 있다.
- 여러 탭 처리는 브라우저 API 대역과 실제 Axios 흐름으로 검증했으며, 실제 두 브라우저 탭을 이용한 수동 검사는 수행하지 않았다.

운영 MySQL에는 자동으로 마이그레이션을 적용하지 않았다.
